# 查询改写

## 模块作用

用户的原始问句不一定适合直接搜索：它可能太短、带有上下文省略，或者包含多个子问题。`query/` 根据上层选择的策略生成更有利于召回资料的查询文本，再交给检索器处理。

查询改写只改变“拿什么文本去搜”，不负责访问 Milvus，也不决定最终答案。

## 常见改写策略

- **直接查询**：保留原问题，适合表达清楚且关键词明确的问题。成本最低，应作为简单可靠的基线。
- **HyDE**：根据问题生成一个假设性答案或描述，再用该文本搜索相似资料。它可能补足术语差异，也可能引入模型猜测，因此搜索结果仍需排序和验证。
- **子查询**：把包含多个方面的问题拆成多个较窄的问题，分别检索后合并候选内容。合并时要去重，避免重复资料挤占上下文。
- **回溯查询**：根据当前追问和对话历史补足省略的对象或主题，使独立检索也能理解问题。

## 文件职责

`rewriter.py` 根据策略名和问题构造一个或多个检索查询。它的输出应有稳定的数据格式，便于 `pipeline/qa.py` 逐个传给 `retriever/`。如果策略名无效或模型改写失败，应有可理解的降级方式，例如退回原始问题。

## 与策略选择的关系

`router/strategy.py` 决定选用哪种检索策略，`query/rewriter.py` 执行该策略。把“选择”和“执行”分开，可以单独比较不同策略的召回与成本；它们都不是入口业务意图识别。

## 评估要点

改写查询数量越多，潜在召回越广，但检索和重排的耗时也会上升。需要在固定评测集上比较原问题与改写查询的召回效果、重复率和总延迟，不能仅凭生成的查询读起来更通顺就认定检索效果更好。
