# RAG 问答模块

## 模块作用

`rag_qa/` 是检索增强问答的核心。它把用户问题转成检索请求，从知识库找相关文本，再把问题和资料交给大模型组织答案。它也包含文档解析切分、查询改写、策略选择、排序以及命令行入口。

RAG 的基本原则是先找资料，再基于资料回答。检索结果质量、上下文组织和提示词都会影响答案；如果没有可靠来源，系统应避免把模型猜测说成知识库事实。

## 问答主流程

```text
用户问题
  → router：判断入口意图或选择处理策略
  → query：按策略改写问题
  → retriever：从 Milvus 召回候选文本块
  → reranker：对候选块重新排序
  → generation：组合问题和上下文，调用大模型
  → pipeline：把各步骤串联并返回结果
```

`pipeline/` 负责协调步骤，但不应把每种检索、模型或存储实现都写进一个大函数。各子模块应完成单一职责，并通过明确的数据结构交换结果。

## 主要子模块

- `router/` 处理入口问候规则、RAG 问题类别、检索策略和代表问句意图检索。BM25+向量模块已接入在线流程，真实意图样本和阈值校准仍依赖项目标注集。
- `query/` 把原问题改写成适合搜索的查询，例如 HyDE、子查询或回溯查询。
- `retriever/` 负责向量化和访问 Milvus，组合稠密与稀疏召回。
- `reranker/` 对初步召回结果进行更精细的相关性排序。
- `generation/` 负责模型调用及提示模板，不负责数据库访问或请求路由。
- `corpus/` 负责把原始文件解析并切分为可入库内容。
- `schema/` 定义 Chunk 等跨模块数据结构。
- `pipeline/` 组织在线问答和集成问答。
- `evaluation/` 提供 JSONL 读取、答案/检索/意图指标、批量 runner、报告保存和基线比较；正式比较仍需本项目人工标注集和稳定基线。

## 数据如何在模块间传递

文档解析后形成带有正文和来源信息的 Chunk；检索器返回候选 Chunk；重排器调整顺序；生成流程取选中的文本作为上下文。这样的传递方式让检索与生成使用同一份来源信息，也为以后加入页码引用、租户字段和评测标注提供统一位置。

## 入口与依赖

`main.py` 用于本地命令行文档处理或交互查询；在线 HTTP 与 WebSocket 请求从 `api/` 进入。RAG 子模块可能依赖本地模型、Milvus 和模型服务，能导入代码不代表外部资源一定可连接。模块是否真正可用要结合部署配置和端到端验证判断。
