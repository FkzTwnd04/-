# 基础设施模块

## 模块作用

`base/` 放置多个业务模块共同依赖、但本身不属于某条业务流程的基础能力。目前主要是配置读取和日志记录。它的目标是让各模块用同一套配置来源和日志格式，避免每个文件各自解析配置、各自创建日志对象。

## 配置是怎样进入程序的

`config.py` 根据项目根目录定位 `.env`，并读取系统环境变量。全部配置按系统环境变量、`.env`、代码默认值的优先顺序取值；`.env` 保存本机真实配置和密钥，不提交到版本库，可提交的模板是 `.env.example`。数据库、模型服务、模型目录和检索参数等模块通过配置对象取得设置。

`.env.example` 只提供变量名和示例占位值，不能放真实密码或 API Key。部署时需要在目标环境自行配置真正的凭据。

## 文件职责

- `config.py` 负责解析配置、处理不同来源的优先级、转换列表等结构化值，并向其他模块提供统一配置对象。配置解析层不负责创建数据库连接或发起模型请求。
- `logger.py` 负责创建应用共用的日志记录器，将日志输出到控制台和文件。调用模块通过它记录运行信息和异常，避免用零散的 `print` 代替服务日志。
- `tracing.py` 为 HTTP 请求设置并传递 `trace_id`，在响应头和服务日志中回传编号，并提供阶段计时工具。当前内部 RAG 子阶段尚未统一埋点，也没有模型 token 成本统计。

## 为什么把配置和日志集中管理

集中配置后，切换开发机、测试机和部署环境时可以改变环境配置而不修改业务代码；密钥也不会散落到各处。集中日志后，排查问题时能使用一致的时间、级别和消息格式。后续追踪功能应建立在统一日志上，而不是让各模块自行拼接不同格式的计时信息。

## 模块边界

基础设施层可被 API、存储和 RAG 模块依赖，但不应反向导入这些业务模块。配置对象可以描述“如何连接数据库”，MySQL 连接本身仍由 `storage/db.py` 创建；日志记录器可以被所有模块使用，但不负责替它们决定业务流程。
